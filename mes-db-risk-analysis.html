ปัญหาคืออะไร: ตารางหลายตัว (เช่น production_scans, oba_records, qc_results) มีคอลัมน์ wo_id ที่ควรจะต้องอ้างอิงไปยัง Work Order จริงๆ ใน work_orders แต่ตอนนี้ยังไม่มีการบังคับ — ทำให้ระบบสามารถบันทึก wo_id ที่ไม่มีอยู่จริงได้ ส่งผลให้ข้อมูลขาดการเชื่อมโยง ตามหา WO ย้อนหลังไม่ได้

สาเหตุที่ยังไม่ได้บังคับตั้งแต่แรก: แอปบางส่วน (โมดูล Workflow และ QC) บันทึกค่า 'WORKFLOW' และ 'QC' เป็น wo_id แทนหมายเลข WO จริง ซึ่งค่าพวกนี้ไม่มีใน work_orders ถ้าบังคับ FK ไปเลยโดยไม่แก้ไข ระบบจะ error ทุกครั้งที่บันทึก

วิธีแก้ที่ทดสอบแล้ว: สร้างแถว WO พิเศษสำหรับค่า synthetic เข้าไปใน work_orders ก่อน (WORKFLOW, QC) จากนั้นเปิดใช้งาน FK ได้สำเร็จทั้ง 11 ตาราง

🟠 ความเสี่ยงปานกลาง — ต้องวางแผนรองรับ
R3 ผ่านการทดสอบ คอลัมน์สถานะ PP เปลี่ยนประเภทข้อมูล

ปัญหาคืออะไร: คอลัมน์ pc_prpo, pc_wait, pc_smt และอีก 5 คอลัมน์ใน pp_projects เดิมถูกออกแบบมาเพื่อเก็บเลขเปอร์เซ็นต์ (เช่น 75.00%) แต่จริงๆ แล้วระบบเก็บเป็น "คำสถานะ" เช่น ON_PROCESS, DONE, DELAY ทีมเพื่อน BE เข้าใจผิดว่าเป็นตัวเลข จึง Schema เก่าเป็น numeric — ตอนนี้แก้เป็น VARCHAR แล้ว

ผลกระทบ: ถ้าโค้ดไหนยังคำนวณตัวเลขบนคอลัมน์นี้อยู่ (เช่น หาค่าเฉลี่ย หรือเปรียบเทียบตัวเลข) จะ error ทันที

✓ ยืนยันแล้ว — ทั้ง 8 คอลัมน์เป็น VARCHAR(30) ครบถ้วน
การดำเนินการฝั่ง my-api

ไม่ต้องแก้เพิ่ม — สแกนโค้ดทั้งโปรเจกต์แล้วไม่มีจุดใดคำนวณตัวเลขบน pc_* (ไม่มี SUM / AVG / เปรียบเทียบ / parseFloat) ทุกที่ใช้เป็นสตริงสถานะเพื่อลงสี Gantt เท่านั้น จึงไม่มีโค้ดที่ error จากการเปลี่ยน type

R4 ผ่านการทดสอบ ประเภทการเปลี่ยนแปลง (Change Request) เพิ่มจาก 4M เป็น 5M+1E

ปัญหาคืออะไร: ระบบ Change Request เดิมรองรับแค่ 4 ประเภท (Man, Machine, Material, Method) แต่ในความเป็นจริงมีการใช้ 2 ประเภทเพิ่มเติม คือ Measurement (การวัด) และ Environment (สิ่งแวดล้อม) Schema ใหม่รองรับครบแล้ว

ผลกระทบ: หน้าจอ dropdown ที่ hardcode ไว้แค่ 4 ค่า จะไม่แสดง 2 ค่าใหม่ ถ้ามีการส่งค่า Measurement หรือ Environment ผ่าน API โดยที่ backend validation ยังไม่ได้อัปเดต จะถูก reject

✓ ยืนยันแล้ว — INSERT ด้วย Measurement และ Environment สำเร็จทั้งคู่
การดำเนินการฝั่ง my-api

อัปเดตครบแล้วทั้ง 3 ชั้น — dropdown หน้าจอมี 6 ค่า (ทั้งฟอร์มสร้างและตัวกรอง) · backend validation รับ 6 ค่า · DB constraint ขยายจาก 4M เป็น 6 ค่าแบบ idempotent (ไม่ลบข้อมูลเดิม)

จึงไม่มีเคสที่ Measurement / Environment ถูก reject

R5 ผ่านการทดสอบ การแจ้งเตือน (Notification) ไม่จำเป็นต้องระบุผู้รับ

ปัญหาคืออะไร: เดิมระบบบังคับว่าทุก notification ต้องระบุ user_id (ส่งให้ใครคนหนึ่ง) แต่ในทางปฏิบัติมีการส่ง notification แบบ "ประกาศทั่วระบบ" ที่ไม่ได้ส่งให้ใครโดยเฉพาะ Schema ใหม่จึงเปลี่ยนให้ user_id เป็น Optional (ค่า NULL = ประกาศทั่วระบบ)

ผลกระทบ: โค้ดที่ดึง user_id จาก notification แล้วใช้โดยตรงโดยไม่ตรวจสอบ NULL จะเกิดข้อผิดพลาด เช่น "Cannot read property of null" หรือ NullPointerException

✓ ยืนยันแล้ว — INSERT notification แบบ global (user_id = NULL) สำเร็จ
การดำเนินการฝั่ง my-api

ไม่ต้องเพิ่ม null check — ระบบแจ้งเตือนที่ใช้จริงเป็นแบบ global ทั้งหมด โค้ดฝั่ง API และหน้าจอไม่มีการอ่าน / filter / เขียน user_id เลย (query ดึงทั้งหมดโดยไม่กรองผู้ใช้) จึงไม่มีจุดที่จะ crash จากค่า NULL

R6 ยืนยันความเสี่ยง — ต้องระวัง บันทึก Audit Log ต้องระบุผู้ทำรายการที่มีอยู่จริงในระบบ

ปัญหาคืออะไร: Schema ใหม่เพิ่มคอลัมน์ actor_id ใน audit_logs เพื่อเชื่อมโยงกับตาราง app_users ซึ่งเป็นสิ่งดีที่ช่วยให้ตรวจสอบย้อนหลังได้ชัดเจนขึ้น

แต่มีข้อควรระวัง: ถ้าโค้ดส่ง actor_id ที่ไม่มีอยู่ใน app_users ระบบจะปฏิเสธการบันทึกทันที (ไม่ใช่แค่ตั้งค่าเป็น NULL อย่างที่เข้าใจไว้แต่แรก) หมายความว่าถ้า module ส่ง user_id ผิด — audit log จะบันทึกไม่ได้เลย ซึ่งอาจทำให้ API ที่เรียก fail ไปด้วย ขึ้นอยู่กับว่า error handling เขียนไว้แค่ไหน

⚠️ ยืนยันความเสี่ยง — actor_id ที่ไม่มีจริงทำให้ INSERT fail ทันที (FK error)
การดำเนินการฝั่ง my-api

ไม่กระทบระบบที่ใช้จริง — audit log ของ my-api บันทึกผู้ทำรายการด้วยคอลัมน์ actor (ชื่อผู้ใช้เป็น VARCHAR, ค่าเริ่มต้น 'system') ไม่ได้ใช้ actor_id ที่เป็น FK จึงไม่เกิด FK error ตามที่กังวล

คง actor_id ไว้ใน schema ตามที่เสนอ (เป็น nullable + ON DELETE SET NULL) เพื่อรองรับอนาคต แต่ยังไม่มีโค้ดใดส่งค่านี้

R7 ผ่านการทดสอบ แบบฟอร์ม Production Plan มีฟิลด์ใหม่ 2 ตัว

ปัญหาคืออะไร: ตาราง pp_projects มีคอลัมน์ใหม่ 2 ตัวคือ pp_type (ระบุว่าเป็นงาน internal หรือ external) และ bom_rec_date (วันที่รับ BOM) ซึ่งเพิ่มมาเพื่อรองรับฟีเจอร์ Dashboard ที่แยกแท็บตามประเภทงาน

ผลกระทบ: การบันทึกข้อมูลยังทำได้ปกติแม้ไม่ได้ส่ง 2 ฟิลด์นี้ (ใช้ค่า default) แต่ข้อมูลที่บันทึกจะไม่ครบ ทำให้ filter/แยกแท็บ Dashboard ไม่ทำงาน

✓ ยืนยันแล้ว — INSERT พร้อม pp_type และ bom_rec_date สำเร็จ
การดำเนินการฝั่ง my-api

รองรับครบแล้ว — ฟอร์มหน้าจอส่งทั้ง pp_type (dropdown internal/external) และ bom_rec_date (ช่องวันที่) · API อ่าน/เขียนทั้งคู่ · Dashboard ใช้ pp_type แยกแท็บได้จริง

คอลัมน์ถูกเพิ่มแบบ IF NOT EXISTS + มี DEFAULT 'internal' แถวเดิมจึงไม่พังและ filter ทำงานได้ทันที

R8 ผ่านการทดสอบ Work Order ใช้หมายเลข (wo_no) เป็นตัวอ้างอิงแทน ID ตัวเลข

ปัญหาคืออะไร: Schema ใหม่ใช้ wo_no (เช่น "WO-2026-001") เป็นตัวระบุหลักของ Work Order แทนที่จะใช้ id ซึ่งเป็นตัวเลขอัตโนมัติอย่างใน Schema เก่า โค้ดที่เชื่อมตาราง (JOIN) ด้วย work_orders.id จะต้องเปลี่ยนมาใช้ wo_no แทน

ผลกระทบ: Query ที่ JOIN ด้วย id จะหาข้อมูลไม่เจอหรือ error แต่ถ้า JOIN ด้วย wo_no จะทำงานได้ถูกต้อง นอกจากนี้ ระบบยังป้องกันการบันทึก wo_no ซ้ำได้ด้วย UNIQUE constraint

✓ ยืนยันแล้ว — UNIQUE constraint บน wo_no ทำงานถูกต้อง ห้ามบันทึกซ้ำ
การดำเนินการฝั่ง my-api — ขอปรับความเข้าใจ

schema v2 ไม่ได้เปลี่ยน PK เป็น wo_no — ตาราง work_orders ยังมี id SERIAL PRIMARY KEY อยู่ และเพิ่ม wo_no VARCHAR(50) NOT NULL UNIQUE เป็นคีย์ธุรกิจควบคู่กัน (มีทั้งสองอย่าง)

ดังนั้นโค้ดที่ JOIN ด้วย id ยังใช้ได้ปกติ ไม่ต้อง refactor · ส่วนตารางลูกใช้ wo_id เก็บค่า wo_no แบบสตริงตามดีไซน์เดิม

สิ่งที่แก้เพิ่ม: พบว่า pre_wo_requests.wo_id ในเอกสาร schema เขียนเป็น VARCHAR ทั้งที่ DB จริงเป็น INTEGER REFERENCES work_orders(id) → แก้เอกสารให้ตรงกับของจริงแล้ว (กัน dev/prod ได้ชนิดต่างกัน)

R9 ผ่านการทดสอบ สิทธิ์ผู้ใช้งานเปลี่ยนจาก 7 ระดับเป็น 3 ระดับ

ปัญหาคืออะไร: Schema เก่ามีสิทธิ์ผู้ใช้งาน 7 ประเภท (PM, STORE, QC, QA, TECH, PD, ADMIN) แต่ Schema ใหม่เรียบง่ายขึ้นเหลือแค่ 3 ระดับ: ADMIN (ผู้ดูแลระบบ), MEMBER (ผู้ใช้ทั่วไป), VIEWER (ผู้ดูอย่างเดียว) โค้ดที่เช็คชื่อสิทธิ์เก่าจะทำงานผิดพลาด

ผลกระทบ: ถ้าโค้ดเช็คว่า role เป็น 'STORE' หรือ 'QC' — ระบบจะตอบสนองผิดเพราะค่าพวกนี้ไม่มีอีกแล้ว ฐานข้อมูลก็ป้องกันไม่ให้บันทึกค่าเก่าด้วย CHECK constraint

✓ ยืนยันแล้ว — ค่าเก่า 'STORE' ถูก reject โดย DB, ADMIN/MEMBER/VIEWER ผ่านปกติ
การดำเนินการฝั่ง my-api

ใช้ 3 role ครบทุกจุดแล้ว — ทั้ง DB constraint, ระบบตรวจสิทธิ์, หน้าจัดการผู้ใช้ และ mock data ใช้ ADMIN / MEMBER / VIEWER สอดคล้องกันหมด ไม่มี mismatch

ส่วน role ชุด 7 ค่า (PM/STORE/QC/QA/TECH/PD) ที่พบในโค้ด เป็นของ backend/ ซึ่งใช้ตาราง users และ ENUM user_role ในฐานข้อมูลของตัวเอง — คนละระบบกัน (ดูรายละเอียดหัวข้อ 3)

3. โค้ดในระบบที่ต้องแก้มือ (พบจากการสแกน)
หลังจากทดสอบ DB แล้ว ได้ทำการสแกนหาโค้ดในโฟลเดอร์ backend/modules พบ 4 ไฟล์ที่ยังใช้ชื่อตารางหรือค่าสิทธิ์แบบเก่าอยู่ ซึ่งจะทำให้ระบบทำงานผิดพลาดเมื่อใช้กับ DB v2
ผลการตรวจสอบเพิ่มเติม — 4 ไฟล์นี้ยัง "ไม่แก้" (และไม่ควรแก้)

ตรวจแล้วพบว่า backend/ เป็นแอปแยกที่มี ฐานข้อมูลและ schema ของตัวเอง (backend/schema.sql) ไม่ใช่แอปเดียวกับ my-api ที่ database_schema.sql (v2) นิยามไว้ — หลักฐานชัดเจน 2 ข้อ:

R9 — Role เก่า close.routes.js — ระบบปิด WO ยังใช้ role เก่า

ที่อยู่: backend/modules/09_close/close.routes.js บรรทัด 21, 63, 109, 298

ปัญหา: กระบวนการปิด Work Order ต้องการการอนุมัติจาก role 'PM' และ 'PD' ซึ่งทั้งสองค่าไม่มีในระบบใหม่ ทำให้ขั้นตอนการอนุมัติจะติดขัดหรือ error

approver_role IN ('PM', 'PD')
ต้องกำหนดใหม่ว่า role ไหนมีสิทธิ์อนุมัติการปิด WO ในระบบใหม่
⚠️ รอทีมตัดสินใจ — ถ้าจะรวมเป็น 3 role ต้องเลือกทาง A หรือ B (ดูด้านล่าง)
ผลตรวจเพิ่มเติม — ทำไมยังไม่กำหนด role ใหม่ทันที

ตรวจโค้ดแล้วพบว่าไม่สามารถ "เพิ่มค่า role" ได้ตรงๆ เพราะติด 2 เงื่อนไข:

1) approver_role เป็นคอลัมน์ ENUM ไม่ใช่ข้อความอิสระ

CREATE TYPE user_role AS ENUM ('PM','STORE','QC','QA','TECH','PD','ADMIN'); -- schema.sql:5 approver_role user_role NOT NULL, -- :533 CONSTRAINT chk_wo_close_approvals_role CHECK (approver_role IN ('PM','PD','ADMIN')) -- :538

การใส่ค่าใหม่ (เช่น MEMBER) ต้อง ALTER TYPE user_role ADD VALUE ก่อน ซึ่ง PostgreSQL ลบค่าออกจาก ENUM ภายหลังไม่ได้ — เป็น migration ที่ย้อนกลับไม่ได้ จึงควรได้รับการยืนยันจากทีมก่อน และต้องแก้ CHECK constraint ควบคู่ด้วย

2) กระบวนการนี้ออกแบบเป็น "อนุมัติ 2 ชั้น" (dual sign-off)

function approvalReadyForClose(a) { return Boolean(a.pm && a.pd); } // ต้องครบทั้ง PM และ PD

ปิด WO ได้เมื่อ PM อนุมัติ + PD อนุมัติ (สองฝ่ายตรวจสอบกันเอง) แต่ในระบบ 3 role มีเพียง ADMIN และ MEMBER ที่ทำรายการได้ และ ADMIN มีเส้นทางปิดแบบข้ามการอนุมัติอยู่แล้ว (isAdminForce) จึงเหลือ MEMBER เติมได้เพียงชั้นเดียว → การควบคุม 2 ชั้นจะกลายเป็นชั้นเดียว ซึ่งเป็นการลดระดับการควบคุมคุณภาพ ไม่ใช่แค่เปลี่ยนชื่อค่า

2 ทางเลือกให้ทีมพิจารณา:

• ทางเลือก A (แนะนำ): คงกระบวนการเดิมไว้ — backend ใช้ฐานข้อมูลของตัวเองที่มี PM/PD อยู่จริง โค้ดส่วนนี้ยังทำงานถูกต้องตามปกติ ไม่มีอะไรพัง

• ทางเลือก B: ถ้าต้องรวมเป็น 3 role จริง ควรเก็บ "2 ชั้น" ไว้แต่เปลี่ยนนิยามจาก role เป็นหน้าที่ (เช่น ชั้นที่ 1 = ฝ่ายผลิต, ชั้นที่ 2 = ฝ่ายวางแผน) แล้วกำหนดว่าใครมีสิทธิ์เติมแต่ละชั้นผ่านคอลัมน์ permissions ของ app_users — วิธีนี้รวมผู้ใช้ได้โดยไม่เสียการควบคุม แต่เป็นงานออกแบบที่ต้องวางแผนร่วมกัน
