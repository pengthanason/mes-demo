✅ ① ผล Checklist 5 ข้อ — ทำจริงได้อะไร
#คำถามเดิมผลจริงที่ได้
① schema mes_web_test มีอยู่แล้วไหม? ✅ ไม่มี → สร้างใหม่
รัน \dn mes_web_test ไม่เจอ → ทำ CREATE SCHEMA IF NOT EXISTS mes_web_test แล้วดำเนินการต่อ
② DB user มีสิทธิ์ CREATE ไหม? ✅ ผ่าน
user postgres เป็น superuser — CREATE ON DATABASE ผ่านทันที ไม่ต้อง grant เพิ่ม
③ schema.sql apply ซ้ำได้ไหม? ✅ ได้จริง
ทุก CREATE TABLE IF NOT EXISTS + ENUM ห่อ duplicate_object — รันซ้ำไม่พังตามที่ทีมยืนยัน
④ Frontend รันที่ port อะไร? ✅ ยืนยัน
Vite frontend = 5101 · backend API = 5100
MES_CORS_ORIGINS=http://localhost:5101,http://127.0.0.1:5101 ตั้งใน .env.mes_web_test แล้ว
หมายเหตุ: localhost:5101/api/... ไม่มี route (Vite ไม่ใช่ server) — ต้องยิง API ที่ localhost:5100 เท่านั้น
⑤ .env.webtest ห้าม commit ✅ ปลอดภัย
.env.* ถูก gitignore จาก commit 0af7ca3 ก่อนเริ่ม — .env.webtest และ .env.mes_web_test ไม่ขึ้น GitHub
⚠️ ② กับดัก 3 ตัว — เจอจริงหรือเลี่ยงได้
กับดัก #1 — schema.sql ไม่ระบุ schema → เลี่ยงได้ด้วย PGOPTIONS
ทำตามคำแนะนำในเอกสาร — apply ด้วย: 
PGOPTIONS="-c search_path=mes_web_test" psql -U postgres \
  -d productiondb_20260721 -f backend/schema.sql
ตาราง 35 ตัวลงใน mes_web_test ถูกต้อง ไม่ชน public
กับดัก #2 — port 5432 vs 15432 → เลี่ยงได้ด้วยการใส่ DB_PORT ชัดๆ
ใส่ DB_PORT=5432 ใน .env.mes_web_test ตั้งแต่แรก — knex migrate ยิงถูก port ไม่มี error
กับดัก #3 — ลืม DB_SCHEMA → เจอแล้ว แก้แล้ว
รอบแรกรัน node server.js โดยไม่โหลด env → DB_SCHEMA ไม่ถูกตั้ง → db.js ไม่ set search_path → query วิ่งไป public.users (ว่าง) → Login failed

แก้: หยุด server แล้วโหลด env ก่อนรัน 
# โหลด env ก่อน (PowerShell)
Get-Content envs\.env.mes_web_test | Where-Object { $_ -notmatch '^#' -and $_ -match '=' } | ForEach-Object { $k,$v = $_ -split '=',2; [System.Environment]::SetEnvironmentVariable($k,$v,'Process') }
node server.js
หลังแก้ login ผ่านทันที
🔧 ③ ขั้นตอน build จริงที่ทำ (พร้อมผล)

0) git pull + ยืนยัน branch

git checkout develop
git pull   # รับ security fix commit 0af7ca3 ที่ทีมแก้ .gitignore

1) สร้าง backend/envs/.env.mes_web_test

# ค่าที่ใช้จริง (password ถูก mask ในเอกสารนี้)
APP_PORT=5100
MES_ENV=development
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=productiondb_20260721
DB_SCHEMA=mes_web_test
DB_SSLMODE=prefer
MES_AUTH_MODE=hybrid
MES_CORS_ORIGINS=http://localhost:3005,http://127.0.0.1:3005,http://localhost:5101,http://127.0.0.1:5101

2) สร้าง schema

psql -U postgres -d productiondb_20260721 \
  -c "CREATE SCHEMA IF NOT EXISTS mes_web_test;"
# → CREATE SCHEMA

3) apply schema.sql พร้อม search_path

PGOPTIONS="-c search_path=mes_web_test" psql -U postgres \
  -d productiondb_20260721 -f backend/schema.sql
# → 35 ตารางลงใน mes_web_test สำเร็จ

4) knex migrate:latest

cd backend
# โหลด env ก่อน (Windows)
Get-Content envs\.env.mes_web_test | ... | SetEnvironmentVariable
npx knex migrate:latest
# → Batch 1 run: 9 migrations ✅  รวมตารางทั้งหมด 45 ตาราง

5) seed users

# bcryptjs hash password แล้ว INSERT ผ่าน psql
INSERT INTO mes_web_test.users (username, password_hash, role)
VALUES
  ('admin',   '$2b$10$...', 'ADMIN'),
  ('member1', '$2b$10$...', 'PD'),
  ('viewer1', '$2b$10$...', 'QC');
# → 3 rows seeded ✅

6) start + verify

node server.js
curl -s localhost:5100/api/mes/health
# → {"status":"ok","version":"0.1.0-station2","database":"reachable",...}

psql -U postgres -d productiondb_20260721 \
  -c "SELECT count(*) FROM information_schema.tables WHERE table_schema='mes_web_test';"
# → count = 45 ✅

📋 ④ Production context — สถานะ finding ล่าสุด
MASKED  ไม่ใช่บั๊ก production — เป็นผลจาก masked copy (ไม่เปลี่ยน)
D03 avg_cost NULL 100% → ยืนยันแล้ว: DB ชุดนี้ต้นทุนถูก null เจตนาก่อนส่งให้ intern ของจริง cost มาจาก Odoo (standard_price mirror) — ห้ามออกแบบให้ cost เป็น source-of-truth ในระบบใหม่
D09 unit_price NULL — ส่วนหนึ่งเป็น legacy VARCHAR จริง ต้องตรวจกับ prod ก่อนสรุป
KNOWN  สถานะล่าสุด
  • A2+A7 / A8 reservation ค้าง (30k / 18.8k) → รากคือ MO close/cancel ไม่สั่ง WMS ปลดจอง · เคยปลดมาแล้ว 261k (17/7) + 904k (2/7) · ⏳ ยังต้อง wire MO→WMS release ระยะยาว
  • DB-15 APD-0690 ZWS → ✅ Wararat แก้ใน PR#59 (21/7) — regexp_replace ลบ U+200B แล้ว · 8 ตัวที่เหลือรอ Odoo sync
  • D13 rfq.customers dedup + code → ✅ DB-11 (17/7) จัดการ dedup 337→322 + Odoo bridge แล้ว · joinable 21.4% · ที่เหลือรอ Odoo populate
  • L1 / L5 / L3 location variants → รากเดียวกับ phantom-location 101k · ⏳ location master + FK = ทางที่ถูก ยังไม่ได้ทำ
DEBT  หนี้ architecture จริงใน productiondb_20260721 — ต้องทำให้ถูกตั้งแต่ต้นใน build ใหม่
  • D10 user 4 ตาราง — ใน productiondb_20260721 มี user กระจายอยู่ 4 ตาราง (wms_users 23 แถวใกล้ headcount จริงสุด) ยังไม่มีตารางกลาง build ใหม่ต้องออกแบบ central user table ให้ทุก module FK มาที่นี่
  • D12 BOM 2 ชุด — productiondb_20260721 มี bom.bom_lines (เก่า) กับ mrp.bom_lines (ใหม่ — join m_items 100% + MO ใช้ตัวนี้) canonical คือ mrp.bom_lines · bom.* ให้ทำ view หรือลบ อย่าเก็บ 2 ชุด
  • D08 trxType camelCase / F1 int vs uuid — naming ใน productiondb_20260721 ไม่สม่ำเสมอ build ใหม่ต้องใช้ snake_case + uuid ตั้งแต่วันแรก อย่าไป rename ตารางใน WMS live — โค้ดอ้างเยอะ เสี่ยงล่ม
  • A3 · D19 · F2/F6 · F4/F5 — column last_event_at, actor_id, created_by มีอยู่ใน productiondb_20260721 แต่ไม่มีใครเขียนค่า build ใหม่ต้อง wire writer (audit / actor_id / timestamp / created_by จาก logged-in user) ครบตั้งแต่ day 1
  • A1 · D04 · D05 — MO ปิดทั้งที่ผลิตไม่ครบ / datecode ขาดหาย / ไม่มี policy ลบ bak · build ใหม่ต้องเพิ่ม guard/constraint (บังคับกรอกเหตุผล / NOT NULL / ลบ bak 14 วัน)
